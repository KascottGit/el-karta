# Suggestions

Reviewing what AI passes (and later rules) propose for a floor, before any of it becomes model data (ADR 0007, PLAN.md principle 6). It is a floor-editor extension (`extension.ts`, registered in `features/floorplan/extensions.ts`); see `features/floorplan/README.md` for how extensions work.

## Pieces

- **Source** (`source.ts`): `SuggestionSource` lists a floor's suggestions (every status, since requirements may already be decided) and sets statuses. `supabase-source.ts` uses `SuggestionRepository`; `createMemorySource` keeps them in memory for tests. The active source is in `suggestionsStore` (`setSuggestionSource` switches it). The list is loaded with TanStack Query under `suggestionsKey(source.id, floorId)`, once per visit; decisions update the cached list. Whoever stores new suggestions (the import flow, the photo analysis) invalidates `['suggestions']`.
- **Views** (`views.ts`): how each kind is shown: its group title and order, the collection the accepted item lands in, a ghost shape, a one-line description. `describe` gets the floor too, so a correction says what it changes: an `opening` whose id is already on the floor reads "Fönster: bredd 1,00 → 1,20 m", a `room-ceiling-height` "Takhöjd i Kök: 2,40 → 2,50 m" (from the room's height, else the floor's). A `device` is named by its type (with the count of sockets in one frame) and ghosted as its type's marker (`features/devices/appearance.ts`) on its wall's face or where it hangs from the ceiling. Payloads are parsed with the kind's schema from the core registry first. A new kind (devices, connections) needs a core `SuggestionKindDef` and a view here; a kind without a view is listed with a generic line and can still be decided on.
- **Layer** (`suggestions-layer.tsx`): ghosts of the pending suggestions on the `overlays` layer, culled by the render window like the model layers: walls as dashed lines of their thickness, openings as dashed spans over their wall (a floor wall or a suggested one), rooms and zones as translucent dashed polygons with their name, devices as their marker, faded. Colour is by confidence (`suggestionStyle` in `canvas/theme.ts`), an issue's colour (`issueColors`) when it has issues, and the selection colour when selected. Ghosts never enter the model, so `floorIssues` never sees them.
- **Tool** (`tool.ts`, "Granska förslag", A): shows the panel. A tap selects the ghost under it, hit-tested in plan coordinates (`ghostAt`: devices before openings before walls before areas), because ghosts are not model items and so not `selectable` nodes. The layer publishes its ghosts to `suggestionsStore` for this. Another feature opens the review with `editorStore.getState().setTool(SUGGESTIONS_TOOL)`.
- **Panel** (`suggestions-panel.tsx`): the selected suggestion, floor-level values (scale, floor height), bulk actions, then one group per kind, each item with its confidence and issues (`issues.<code>`, with the issue's params).
- **Actions** (`actions.ts`), as pure functions over a source and a `QueryClient`, so they are tested without React.

## Decisions

- **Acceptable** means pending, of a registered kind, with a payload that fits it, and the same for every pending requirement, with no rejected or missing requirement (`createBlockers`). Only acceptable suggestions get an accept button and go into the bulk accepts and their counts; the others show why and can only be rejected.
- **Accepting** is `acceptSuggestions` from core: the suggestions plus their pending requirements become one `apply(edit)`, so one undo step, then their rows are marked accepted. When it pulls in requirements, the panel asks first, with the count. If marking fails, the edit stays, the rows stay pending and the panel says so; accepting again puts the same items by id, so nothing is duplicated.
- **Undo and redo follow the rows.** An accept remembers the history entry it pushed (`accepts` in `suggestionsStore`). When undo moves that entry to the model store's `future`, its rows go back to pending and their ghosts return; when redo moves it back, they are accepted again. Once the entry leaves the history (a new edit after undo, the history limit, another project), it is no longer followed.
- **"Godkänn och redigera"** accepts one suggestion and selects the item it became with the select tool (`editTarget`). Floor-level values have no item and only offer accept and reject.
- **Rejecting** a suggestion also rejects the pending suggestions that require it, directly or through others, since they could never be accepted. The panel asks first, with the count.
- **"Godkänn säkra"** accepts the acceptable suggestions at or above the threshold (default `suggestionStyle.thresholds.high`, 80 %) whose pending requirements reach it too, so a bulk accept never pulls in a less certain scale or wall. A suggestion without a confidence counts as below every threshold above 0.
- **Review prompt.** With the select tool, a floor with pending suggestions shows "N förslag att granska" and a button to the review tool. Panels' `visible` sees only the editor and model stores, so the layer, which publishes the pending count, nudges the editor store when the count changes.

## Dev and e2e

In development builds, `?suggestions` in the URL (e.g. `/dev/synthetic/small?suggestions`) uses a memory source seeded with `dev-seed.ts`: a scale, a floor height and a 4 × 3 m bedroom with a door and a window beside the floor's walls. `apps/web/e2e/suggestions.spec.ts` uses it.
