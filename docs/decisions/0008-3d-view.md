# 0008 3D view

Status: accepted (M9); editing in 3D amended by ADR 0009 (M9b)

## Decision

The 3D view (`apps/web/src/features/view3d/`) is a react-three-fiber canvas that shows the same model and the same selection as the 2D editor. Editing stays in 2D.

- **A view mode of the floor editor.** The editor shows 2D, 3D or both side by side (`?view=3d|split`, `features/floorplan/view-mode.ts`). Both views read and write the editor store's `selection`, so there is no syncing code. The editor works on one floor, so a tap on an item on another floor opens that floor with the item selected (`openFloor(floorId, selection)`). The 3D code is a lazy chunk; three.js loads only when 3D is opened.
- **Pure geometry, thin rendering.** `view3d/geometry/` turns floor data into boxes and outlines with plain numbers and no three.js import, so it is unit-tested like core geometry. Walls are split along their length around openings (pieces between openings, a sill piece under windows, a lintel above each opening) instead of using a CSG library: openings are always rectangles in a straight wall, so splitting is exact and cheap. A wall end that meets another wall's end is extended by half its thickness, which closes L and T corners without mitring; an end continued in a straight line by another wall is not, since the two are already continuous. Ceilings are not drawn.
- **Few draw calls.** Per floor, all wall pieces are merged into one geometry and all room slabs into another, each with a triangle → item id table. Devices are one `InstancedMesh` per marker shape with an instance → device id table. A floor's meshes are rebuilt only when its `FloorData` object changes, which Immer guarantees only happens for the edited floor. The selection is drawn as a separate highlight of just the selected items, so selecting never rebuilds the merged geometry. The canvas renders on demand (`frameloop="demand"`).
- **Picking** runs the 2D editor's gesture controller (`canvas/gestures.ts`) on the 3D canvas's pointer events, so taps, drags and multi-touch follow the same rules and `DRAG_THRESHOLD` as in 2D; drags and pinches are left to the orbit controls. A tap raycasts the visible floors' meshes and maps `faceIndex` and `instanceId` back to items through the id tables (`SceneRegistry.pick`).
- **Devices share one appearance registration** (`features/devices/appearance.ts`): marker shape and colour per `domain:type`, with a domain and a generic fallback, used by the 2D device layer and the 3D view. Devices in a container (breakers in a panel) have no marker of their own. A device with a floor placement and a `size` (furniture) is drawn as its footprint in 2D and as a box in 3D. `FloorPlacement.size` is x width, y depth, z height in metres, centred on `at`; `rotation` is in degrees from plan +x towards +y (clockwise on screen), the same sense as the background's rotation.

## Why

Keeping 3D read-only and on the shared selection gives the "select in one view, see it in the other" behaviour for free and keeps one way of editing. Merged geometry and instancing are the standard three.js answers to many small objects; the large synthetic project has thousands of walls and 8,000 devices, which as separate meshes would mean thousands of draw calls per frame.
