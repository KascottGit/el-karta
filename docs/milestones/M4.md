# M4 – AI pipeline and floor plan import

Status: **implemented** and deployed to el-karta-dev; first real-model evals recorded (free tier: 20 requests per model per day), estimate-mode run pending. Milestone branch: `m4-ai-import`.

From PLAN.md: provider adapter (start with one provider; Gemini free tier with test data only is fine), `packages/ai-passes` with the pass interface, the `ai-pass` Edge Function, validate-and-retry-once loop, `ai_runs` logging. Floor plan pass: walls, openings, rooms with names and types, dimension text → scale (fallback: user measurement). Generic suggestions UI (ghosted overlay; accept/edit/reject, per item and in bulk). Large drawings are split into tiles and merged by code. Eval harness in `evals/` with the first 20 plans and hand-traced ground truth.

**Done when:** the eval scores are recorded per model, a typical Swedish estate-agent plan gives a usable model that needs only minor fixes, and a bad AI result can always be rejected and drawn by hand instead.

## Design decisions for this milestone (approve with the plan)

1. **The LLM reads meaning, code does geometry (principle 7).** Typical plan pages also hold a legend, a site map and a building section. The pass first asks for the bounding box of the main floor plan, and the browser crops to it (with a margin) before the detail call, so small plans get full resolution and insets are ignored. The detail call asks the model for image-space data only: wall segments, openings, room labels (name, type, a point inside the room) and dimension texts (value and the two pixel ends they measure), in coordinates normalised to 0–1000 on the image. Deterministic code in `packages/ai-passes/src/floorplan/` then:
   - converts pixels to metres with the background placement (`geometry/background.ts`) and the scale;
   - finds the plan's main orientation (one test plan is turned about 25°) and cleans walls: snap walls near that orientation or its perpendicular to it, merge endpoints within a tolerance, merge collinear overlapping segments, drop fragments shorter than ~0.3 m;
   - projects each opening onto its nearest wall (core `geometry/opening.ts`) and clamps it inside the wall;
   - builds room polygons with core `fillRoom` from the label point; if the walls around it don't close, the room becomes a suggestion with the model's rough polygon and a flag, never a silent guess.
2. **Scale: printed information first, then optional user input, then an AI estimate.** Many estate-agent plans have no dimension lines. The model reports what it sees, and code computes a metres-per-pixel value from each piece:
   - **printed** (`source: 'dimension_text'`): a printed ratio ("Skala 1:100 (A4)") together with the PDF page size from pdf.js (the most reliable; most test plans have it), dimension texts with their two pixel ends, a scale bar (its tick labels and pixel positions), a total area ("Area ca 23 m²") against the sum of the room areas, and room area texts ("CA 19 m²", compared with the room polygon's pixel area). With two or more that agree within 5 %, their median is used.
   - **user** (`source: 'user'`): if nothing printed is found, or the printed values disagree, the import offers the existing scale tool ("Jag vet ett mått"), but it can be skipped ("Jag vet inget mått").
   - **estimate** (`source: 'ai_estimate'`): the model reports the pixel size of objects with standard sizes: interior doors (≈0.8–0.9 m leaf), entrance doors (≈1.0 m), wardrobes "G" (0.6 m), kitchen counters (0.6 m deep), beds, toilets, bathtubs. Code turns each into a candidate with a typical size per type (a table in the pass, not in the prompt) and uses the median, with a confidence from how widely the candidates spread. A floor whose scale is an estimate shows a permanent "Uppskattad skala – kontrollera ett mått" notice with a shortcut to the scale tool, so a guess is never shown as fact (principle 8). Re-scaling later moves everything that was accepted from the import.
   - Door widths outside 0.6–1.2 m under the chosen scale raise `scale.door-width-implausible`. A floor that already has a user scale keeps it.
   - Printed ceiling heights ("rumshöjd ca 2,55 m") become a suggested floor height.
3. **Suggestions are stored, not written into the floor.** A new `suggestions` table (one row per suggested item: `project_id`, `floor_id`, `run_id`, `pass`, `kind`, `payload jsonb`, `confidence`, `issues jsonb`, `status` pending/accepted/rejected), with RLS through `can_read_project`/`can_write_project` and a pgTAP test. They survive reloads and can be reviewed by another project member. `kind` is open (`wall`, `opening`, `room`, `scale` now; `device`, `connection` from M11/M12), and each kind registers a Zod payload schema and an accept function, so later passes reuse the table and the UI unchanged.
4. **Accepting is a normal edit.** `acceptSuggestions(ids)` turns the payloads into one `applyEdit` (so undo works and autosave saves it) and marks the rows accepted. Accepted items get `provenance: { status: 'confirmed', source: 'ai:floorplan:<model>', confidence }`. Payloads reference each other by suggestion id (an opening points at a suggested wall), and accepting an opening also accepts its wall. "Edit" means accept and select the item in the editor; editing the suggestion itself before accepting is out of scope.
5. **Provider adapter in a package, not only in `_shared/`.** `packages/ai-providers` holds `generateStructured({ model, system, messages, images, schema })` with a Gemini implementation (the official `@google/genai` SDK, which runs in Deno and Node) and a fake provider that replays fixtures. Keeping it in a package, rather than in `supabase/functions/_shared/ai/` as PLAN.md sketches, lets the eval runner in Node call the exact same code. The Edge Function imports it through the import map in `supabase/functions/deno.json`. JSON Schema for structured output comes from Zod 4's built-in `z.toJSONSchema`. A short ADR records this.
6. **Tiling in the browser, merging in the pass.** Images larger than ~2000 px on the long side are cut in the browser into overlapping tiles (~15 % overlap). Each tile is one `ai-pass` call (keeps each call well inside Edge Function time limits); the client then runs the pass's pure `merge` (tile offsets back to full-image coordinates, de-duplicate walls and openings in the overlap, then the cleanup from decision 1) and stores the merged suggestions through the function's `commit` step. Small images are one call with no merge.
7. **Edge Function `ai-pass`** runs as the signed-in user (ADR 0004): it checks write access, enforces a per-user rate limit (count of the user's `ai_runs` in the last hour, default 30), takes the image or tile from the request body (the browser already has it for tiling; size-capped at 4 MB), runs the pass (call → Zod parse → validate → if errors, one retry with the issues → result with remaining issues flagged), logs `ai_runs` (adding `floor_id`, `duration_ms` and `error` columns) and returns the parsed output. Provider keys are Supabase secrets only. `AI_PROVIDER=fake` in the local stack makes integration and e2e tests deterministic and free.
8. **Models.** Gemini only in M4. Each pass names its default model in `packages/ai-passes/src/config.ts`; the eval runner takes `--model` to compare. We compare the current Gemini Flash and Pro models.
9. **Evals, starting with the 8 plans in `floorplans/` (deviation: PLAN.md says 20; more are added as they turn up).** Ground truth comes in two levels, so scoring works before anyone traces a plan:
   - **Light facit** (`evals/floorplan/facit/*.json`, format in `evals/floorplan/README.md`), written by the orchestrator in T0 by reading each plan and checked by the person: rooms (name as printed, accepted types, printed area), door count, rotation, total area, and the scale as `metresPerImageWidth` (resolution-independent) where something printed gives it. Scores: room count, name and type accuracy, door count, scale error.
   - **Estimate mode** (`--estimate-scale`): hides printed scale information from the scale chain on plans whose true scale is known and scores the estimate, since only one test plan has no printed scale at all.
   - **Full facit** (optional per plan): the AI result after the person has corrected it in the editor, exported with a dev-only "Exportera facit" action. It adds wall-length and room-area error, and the number of corrections needed is itself the "only minor fixes" measure.
   - `evals/floorplan/` holds `manifest.json` (file name, source, checksum), the facit files and a pure, unit-tested scoring module. `pnpm eval floorplan --model <id>` runs locally (needs `GEMINI_API_KEY` in the shell) and appends a row per plan and model to `evals/results/floorplan.csv`.
   - Plan images are **not** committed (the repo is public). They stay in the git-ignored `floorplans/`, which the manifest points to.
10. **Dependencies:** `@google/genai` (runtime, `packages/ai-providers`). Nothing else; tiling uses the browser canvas, JSON Schema comes from Zod.

### T1 – Provider adapter and pass runner

- **Depends on:** T0
- **Touches:** `packages/ai-providers/**`, `packages/ai-passes/src/run.ts` (+ tests)
- **Read:** ADR 0004, ADR 0007
- **Goal:**
  - Gemini implementation of `generateStructured`: images inline, JSON Schema output, token counts, retry with backoff on 429/503 (max 3), typed errors (`rate_limited`, `invalid`, `error`).
  - `runPass(pass, input, provider)`: select context → prompt → call → Zod parse → `validate` → one retry with the issues (and parse errors) appended → result with remaining issues, token and retry counts for `ai_runs`.
- **Acceptance:** runner tests with the fake provider cover: valid first time, fixed on retry, still invalid after retry (issues returned, no third call), unparseable output, rate limit. The Gemini adapter is tested against a mocked `fetch`.
- **Out of scope:** other providers.

### T2 – Database and Edge Function

- **Depends on:** T1
- **Touches:** `supabase/migrations/**`, `supabase/tests/**`, `supabase/functions/**`, `packages/data-supabase/**`
- **Read:** ADR 0004, ADR 0007, AGENTS.md "Database and secrets"
- **Goal:**
  - Migration: `suggestions` table with RLS; `ai_runs` gets `floor_id`, `duration_ms`, `error`; regenerate DB types.
  - `ai-pass` function with two actions: `run` (one image or tile → parsed output) and `commit` (merged suggestions → `suggestions` rows). Rate limit, request size cap, `ai_runs` logging.
  - `SupabaseRepository` (or a small `SuggestionRepository` next to it): list a floor's pending suggestions, set status, invoke the function.
- **Acceptance:** pgTAP: a non-member sees no suggestions and a viewer can't change their status. Integration test against the local stack with `AI_PROVIDER=fake`: a run logs `ai_runs`, a commit creates rows, the 31st run in an hour is refused.
- **Out of scope:** UI.

### T3 – Floor-plan pass

- **Depends on:** T0 (parallel with T1)
- **Touches:** `packages/ai-passes/src/floorplan/**` (+ tests, fixtures)
- **Read:** ADR 0006 (wall and opening conventions), ADR 0007
- **Goal:** the pass definition: output schema, prompt (Swedish room names → `RoomType`, e.g. "Sovrum", "Kök", "Rum", "Allrum", "Hall", "WC/D", "Dusch", "Tvätt", "Klk"; abbreviations "G", "K/F"; dimensions in mm and m; "CA 19 m²"), validators, `toSuggestions` with the geometry of decision 1, the scale chain of decision 2 (printed → user → estimate, with the typical-size table), tile `merge` from decision 6.
- **Acceptance:** unit tests on hand-written model outputs: plan-region crop box with margin, wall cleanup on an axis-aligned and a rotated plan (orientation snapping, endpoint and collinear merging), openings projected and clamped, rooms filled from a label point and flagged when open, scale from a printed ratio and page size, dimension texts, a scale bar, total and room area texts (agreeing and disagreeing), an estimate from standard objects with its confidence, door-width sanity issue, merging two overlapping tiles without duplicates.
- **Out of scope:** calling a real model.

### T4 – Generic suggestions UI

- **Depends on:** T0 (parallel with T2)
- **Touches:** `apps/web/src/features/suggestions/**`, one line in `features/floorplan/extensions.ts`
- **Read:** `features/floorplan/README.md`, ADR 0006
- **Goal:**
  - A floor-editor extension that draws pending suggestions ghosted (by kind, through the kind registry) on the overlays layer, selectable like normal items.
  - A side panel: list grouped by kind with confidence and issues; accept / reject per item; accept all, reject all, accept all above a confidence threshold; "Godkänn och redigera" selects the accepted item.
  - Works with an in-memory suggestion source so it is testable without the database.
- **Acceptance:** accepting is one undo step; rejecting all leaves the floor unchanged; accepting an opening accepts its wall; ghosted items never appear in validation of the real floor; touch e2e on 390×844.
- **Out of scope:** how suggestions are produced.

### T5 – Floor-plan import flow

- **Depends on:** T2, T3, T4
- **Touches:** `apps/web/src/features/floorplan/ai-import/**`, `features/floorplan/background/**` (scale notice and re-scaling), `packages/core/src/edits/` (`scaleFloor`), one line in `extensions.ts`
- **Goal:** "Tolka planritning med AI" on a floor with a background: locates and crops the plan region, passes the PDF page size along when the background is a PDF page, tiles the crop if it is still large, calls `run` per tile with progress and cancel, merges, commits, opens the suggestions panel. If no printed scale was found, it asks "Vet du ett mått?" with the scale tool or "Uppskatta åt mig"; an estimated scale shows the notice from decision 2. Changing the scale of a floor later offers to scale its walls, openings and rooms with it (a core edit `scaleFloor(factor, origin)`, so a corrected estimate fixes the whole floor at once). Errors and rate limits are shown in Swedish; the floor stays editable by hand throughout.
- **Stale suggestions:** walls and rooms require the scale suggestion they were measured with (ADR 0007), so accepting one sets that scale. If the person sets or changes the floor's scale while suggestions are pending, the import re-interprets the stored model output with the new scale (replacing the pending rows) instead of letting an accept overwrite the person's scale (decision 2). Keep the last run's merged output for this (e.g. on the run or in the commit).
- **Acceptance:** unit tests for tiling (tile count, overlap, offsets) and `scaleFloor`; e2e with `AI_PROVIDER=fake`: import → suggestions → accept some → reload → accepted items saved, rejected gone.

### T6 – Eval harness

- **Depends on:** T1, T3
- **Touches:** `evals/**`, root `package.json` script `eval`, dev-only "Exportera facit" in `apps/web/src/features/floorplan/dev/**`
- **Goal:** decision 9: ground-truth format and export, manifest, scoring, runner, results CSV.
- **Acceptance:** scoring unit-tested on hand-made pairs (perfect, missing room, wrong type, scale off by 10 %); the runner works end to end with the fake provider in a test.
